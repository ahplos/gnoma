.Features demonstrated
****
* Gnoma Chart templates.
* Gnoma Chart helper templates.
* Gnoma Chart template helper attributes.
* Gnoma Chart built-in variables.
****

The Gnoma Chart aims to define basic Kubernetes resources for application deployments out-of-the-box and provide as many reasonable defaults as possible to reduce the amount of boilerplate required by the end user.  The Gnoma Chart also aims to do away with the need to write Helm (Go) templates, and instead follows the Helm requirement for values.yaml files be https://helm.sh/docs/chart_template_guide/values_files/[plain YAML].

NOTE: The example below is purposefully contrived to be more complicated than necessary.  In this case the Ingress will be communicating with the Service over port 8081, and the Service will forward incoming requests to Apache Web Server container over the more standard port 8080.  The next part of the tutorial will make it clear why we are making this more complicated than necessary.

[discrete]
==== Create and save the following file as `gnoma-demo-1.yaml`

[source,YAML,linenums]
----
gnomaTemplates: # <.>
- templateName: deployment # <.>
  image: registry.redhat.io/rhel8/httpd-24

- templateName: service # <.>
  port: 8081 # <.>
  targetPort: 8080 # <.>

- templateName: ingress # <.>
  host: httpd-$<HELM_RELEASE_NAMESPACE>.apps-crc.testing <.>
  port: 8081 # <.>
----
<.> All Gnoma Chart templates are defined in a list called `gnomaTemplates`.
+
TIP: **If you want to spread your Gnoma templates out over multiple values.yaml files, more template lists can be defined as `gnomaTemplates-*`; e.g. gnomaTemplates-foo.**
+
The suffix is meaningless and only serves to be keep the lists unique from Helm's perspective. Gnoma Chart will automatically merge the lists into a single, unified list.
<.> By convention, there is a one-to-one relation between Gnoma Chart templates and the Kubernetes resources they render.
... `deployment` for a Kubernetes Deployment
... `service` for a Kubernetes Service
... `ingress` for a Kubernetes Ingress
... Gnoma Chart templates are all named by convention with lowerCamelCase.

<.> _Helper attributes_ are Gnoma Chart template top level keys; e.g. some standard Gnoma attributes every template has:
... `templateName`: the name of the Gnoma Chart template to render.
... `objName`: maps directly `metadata.name`.
... `template`: custom Gnoma template definitions when built-in templates aren't used.

<.> `$<HELM_RELEASE_NAMESPACE>` references a built-in Gnoma Chart variable.
... In a Helm template this corresponds to https://helm.sh/docs/chart_template_guide/builtin_objects/[`.Release.Namespace`]; i.e. the namespace a Helm chart is deployed in.
+
NOTE: The release namespace is not necessarily the same as the Kubernetes resources being deployed.
... Gnoma Chart variables are referenced using the syntax `$<__VARIABLE_NAME__>`.
... Gnoma Chart conventions define variables using UPPER_SNAKE_CASE, similar to Shell.

==== Tutorial steps

.What to expect
****
* A https://kubernetes.io/docs/concepts/workloads/controllers/deployment/[Deployment], https://kubernetes.io/docs/concepts/services-networking/service/[Service], and https://kubernetes.io/docs/concepts/services-networking/ingress/[Ingress] will be deployed on the cluster using Gnoma Chart.
* An httpd https://kubernetes.io/docs/concepts/workloads/pods/[Pod] will be created from the Deployment and accessible in the browser from outside the cluster.
* The httpd server's test page will be reachable and visible in the browser.
****
